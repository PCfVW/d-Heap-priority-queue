# Phase 3.5 — Per-Section Timing Attribution

Generated by `benchmarks/scripts/aggregate/` from 10 timed `--profile-sections` repetitions (K=2 warmup discarded) per `(language, graph, arity)` cell — the same protocol Phase 3's wall-time table uses, reused here after the original single-un-iterated-call design proved too noisy to attribute cross-language gaps (see `CHANGELOG.md`). Each number below is the **median** across those repetitions. See [`methodology.md`](../methodology.md#phase-35-per-section-timing) for the mechanism and the cross-language section-boundary contract. All 120 `.profile.jsonl` cells (8 graphs × 3 arities × 5 languages) are on disk in `benchmarks/results/<Language>/`; the tables below focus on the headline `huge_dense × d=8` cell per methodology.md.

**Measurement environment:** captured 2026-08-30 on the same CPU model as the Phase 3 baseline rig (AMD Ryzen 9 5950X, 64 GB RAM, Windows 11), independently confirmed via `Win32_Processor` rather than assumed from the (older, unregenerated) `env-*.json` files. Run on the default "Balanced" power plan in a shared sandbox, not methodology.md's recommended quiesced "High performance" setup — absolute numbers may carry more variance than a tuned run; cross-language ratios are the meaningful signal.

## Finding

On `huge_dense × d=8`, median-of-10 Rust total (23797.7 µs) exceeds Go's (13508.4 µs) by 10289.3 µs. `relax` is 1.31× Go's on Rust, versus 1.52× on `pop` — NOT clearly concentrated in `relax` relative to the heap-only sections even after repeated sampling — the hashmap hypothesis is not confirmed by this data alone; see the caveats below before drawing conclusions.

Repeated sampling (K=2 warmup / N=10) was adopted specifically because Phase 3.5's original single-call design produced a result (Rust's heap-only `pop` showing a *larger* relative gap than the hashmap-heavy `relax`) that looked like noise, not signal. Total-time IQR across the 10 reps: Rust 645.4 µs, Go 973.3 µs — both comfortably under 15% of their own median, so the medians above are a reasonably stable summary of this machine at this point in time.

**Caveats specific to this run:**
- Go's `time.Since` on Windows quantizes to a coarse grid (documented in methodology.md's Phase 3 timer-resolution caveat); individual `contains`/`increase_priority` calls are often faster than that resolution, so Go's `inc_pri` (and occasionally other sections) can under-report on any given rep — a measurement floor, not zero real cost. The median across 10 reps reduces but does not eliminate this.
- Phase 3.5 timer overhead (~50–200 ns per main-loop iteration, per methodology.md) is symmetric across languages but not subtracted from any number above, and repeated sampling doesn't change that — it reduces cross-rep noise, not the overhead itself.
- Section-timing medians are still not directly comparable to `results/SUMMARY.md`'s `huge_dense` wall-time medians — the section timers themselves add overhead the plain wall-time measurement doesn't pay.

## Timer call overhead (instrument floor)

Median per-call cost of this process's own native monotonic-timer read, from 10 independent batches of 1,000,000 back-to-back `--timer-overhead` calls. Every Phase 3.5 section pays roughly one "bracket" (2 calls: start + elapsed) per section per main-loop iteration, so this is the floor beneath every number in the tables above — it answers whether the cross-language section differences could be an artifact of differing instrumentation cost rather than real algorithmic differences.

| Language | Median per-call (ns) | Ratio | Median per-bracket (ns) | IQR (ns) |
|---|---:|---:|---:|---:|
| Go | 4.6 | 1.00× | 9.2 | 0.5 |
| Cpp | 18.8 | 4.11× | 37.7 | 0.3 |
| Zig | 23.7 | 5.17× | 47.4 | 0.2 |
| Rust | 25.3 | 5.52× | 50.6 | 0.1 |
| TypeScript | 43.2 | 9.43× | 86.5 | 0.4 |

Go's timer read is the cheapest of the five; TypeScript's is 9.4× more expensive per call. On `huge_dense × d=8` the main loop pays on the order of 10⁵ brackets total across `setup`/`pop`/`relax`/`inc_pri` combined (`pop`/`relax` alone are bounded by \|V\|=2500 and \|E\|=125000 respectively), so even this small a per-call difference compounds to a real, non-zero, systematic offset between languages — but at nanoseconds per call against the Finding's microseconds-to-milliseconds section totals, it is one to two orders of magnitude too small to be the primary explanation for the Rust-vs-Go gap on its own. It is a genuine confound this document does not correct for.
